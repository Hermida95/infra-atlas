An admission webhook is an HTTPS service the API server calls with an AdmissionReview containing
the object being written. A mutating webhook may return a JSON patch; a validating one may return
allowed or not allowed with a message. This is how sidecar injection, policy enforcement, image
digest pinning and defaulting are all implemented.

**It is a dependency of every write it matches**, and this is the source of every webhook horror
story. With `failurePolicy: Fail` and a service that is down, every matching request is rejected.
If the match rule is broad enough to include the webhook's own Deployment, or the kube-system
namespace, or Pods generally, you cannot deploy the fix -- the cluster will not accept the write
that would repair it. Recovery then means deleting the webhook configuration directly, which
requires an identity that still works.

**So the safety rules are mechanical and worth treating as non-negotiable.** Scope `rules` to the
specific resources and operations you need. Exclude kube-system and the webhook's own namespace
with a `namespaceSelector`. Keep `timeoutSeconds` to one or two. Run at least two replicas with a
PodDisruptionBudget and a topology spread. Use `Ignore` unless the policy genuinely must be
unbypassable, and when it must, accept that you have coupled cluster writability to that
service's uptime and plan accordingly.

**Latency is cumulative and invisible.** Every matching request waits for the webhook. Several
webhooks matching Pod creation, each taking 200ms, adds nearly a second to every Pod creation in
the cluster -- which shows up as slow scaling and slow rollouts with no obvious cause. The API
server's `apiserver_admission_webhook_admission_duration_seconds` metric is where that is
visible.

**Before writing your own, check whether you need to.** ValidatingAdmissionPolicy handles
validation in-process with no service to run. Kyverno and Gatekeeper handle mutation and
generation with a policy language, tested by many clusters. A hand-written webhook is justified
when the logic is genuinely specific to your organisation -- and even then, the hard parts are
certificate rotation, idempotent patches and ordering, not the business rule.
