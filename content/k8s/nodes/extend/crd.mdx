A CustomResourceDefinition registers a new kind with the API server. Apply it and you
immediately have a working resource: validated, versioned, watchable, RBAC-controlled, visible to
`kubectl`, stored in etcd. You get the entire API machinery for the cost of a schema, which is
the single most important extensibility decision Kubernetes made.

**And nothing happens.** A custom resource is a record. Creating a `Database` object produces no
database until a controller is watching that kind and acting on it. The most common confusion
after installing a CRD -- objects accepted, nothing occurring -- is exactly this, and the
diagnosis is whether the operator's Deployment is running.

**The schema is where the quality is.** A structural `openAPIV3Schema` with types, required
fields, enums, defaults and `x-kubernetes-validations` CEL rules means mistakes are rejected at
apply time with a useful message, instead of becoming a controller crash loop an hour later.
Without a schema the API accepts anything that is YAML. `status` as a subresource is the other
piece of hygiene: it separates what users write from what the controller writes, so RBAC can
grant them separately and a user cannot overwrite status by re-applying their file.

**Versioning is a promise you are making.** Once a version is served, something will depend on
it. Serving two means providing a conversion strategy -- `None` only works if the schemas are
compatible field-for-field, otherwise a conversion webhook, with all the availability
considerations any webhook has. Starting at `v1alpha1` and being honest about it is far better
than shipping `v1` and breaking it.

**Operationally, two things bite.** Deleting a CRD deletes every object of that kind, instantly
and cluster-wide -- a one-line command that can remove every `Certificate` or every
`Database` in the cluster. And custom resources with finalizers whose controller has been
uninstalled can never be deleted, which is the usual reason a namespace is stuck
`Terminating` forever.
