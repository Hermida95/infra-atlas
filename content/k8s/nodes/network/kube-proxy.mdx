kube-proxy runs on every node and watches Services and EndpointSlices. When they change, it
rewrites the node's packet-filtering rules so that traffic to a ClusterIP or a NodePort is
destination-NATed to a Pod address. It does not sit in the data path -- the kernel does the work
-- which is why there is no proxy to overload and no hop to measure.

**Its weakness is rule-set size, not throughput.** In iptables mode, each Service produces a
chain and each endpoint a rule, and the whole set is re-synced on changes. At a few hundred
Services this is invisible. At several thousand, with churn, the sync takes seconds, during which
new endpoints are not yet programmed -- which appears as connections to recently started Pods
being refused, or to deleted ones hanging. IPVS and nftables modes exist to fix exactly that,
with hash-based lookup and incremental updates.

**The SNAT behaviour is worth knowing because it hides client IPs.** With
`externalTrafficPolicy: Cluster`, traffic entering a node for a Pod elsewhere is source-NATed so
the reply comes back the same way -- so the receiving Pod sees a node IP as the client. Anything
that needs the real client address (rate limiting, geo rules, audit logging) needs
`Local`, an IP-target-mode cloud load balancer, or an Ingress controller that sets
`X-Forwarded-For`.

**Replacing it is now a normal choice.** Cilium's kube-proxy replacement implements Services in
eBPF, attaching at the socket level so a connection from a Pod to a ClusterIP is translated
before a packet is even built. That removes the DNAT, removes the rule traversal, and preserves
the source address -- at the cost of a newer kernel and a tighter coupling to the CNI.

For debugging in iptables mode, `iptables-save | grep <service-name>` on the node shows the chain
and whether the endpoints you expect are in it; a Service whose EndpointSlice is correct but
whose chain is stale points at kube-proxy itself, which is one of the few times restarting a
DaemonSet Pod is the actual fix.
