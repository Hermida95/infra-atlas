A service mesh intercepts all traffic between Pods with proxies it controls, and uses that
position to provide encryption, retries, timeouts, circuit breaking, per-request routing and
telemetry -- none of it requiring application changes. For a large estate of services in several
languages, that is a serious amount of consistency bought in one place.

**The tax is the honest part of the conversation.** A sidecar per Pod costs 50-200 MiB of memory
and some CPU on every replica, which across hundreds of Pods is a real line in the bill. It adds
two proxy hops per call, so p99 latency moves. It owns your traffic path, which means a mesh
upgrade is a traffic event and a misconfigured policy is an outage. And it is a substantial
amount of new vocabulary for everyone who debugs production.

**Sidecar-less modes change the arithmetic.** Istio's ambient mode splits the work: a per-node
component handles mTLS and L4, and an L7 proxy is added only for the namespaces that need HTTP
features. Cilium does the L4 and identity work in eBPF with no proxy at all. Both reduce the
per-Pod cost to near zero for workloads that only wanted encryption, which is the majority.

**The decision is best made feature by feature.** If you want mTLS between services, ambient mode
or a CNI with transparent encryption does it for a fraction of the cost. If you want
retries and timeouts, a good client library does it with no infrastructure. If you want traces,
instrumenting with OpenTelemetry gives better spans than a proxy ever will, because the proxy
cannot see inside your process. A mesh earns its place when you need *all* of it, *uniformly*,
across teams that will not adopt a library -- and that is a real situation, just not the common
one.

**If you do adopt one**, two rules save most of the pain: roll it out namespace by namespace with
permissive mTLS first, so an un-meshed client is not instantly broken; and keep NetworkPolicy
underneath, because a Pod without a working sidecar should not be a Pod without any policy.
