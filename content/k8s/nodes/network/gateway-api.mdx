Gateway API is the replacement for Ingress, built by the same community after a decade of
watching Ingress annotations become an unportable dialect per controller. The things that used to
be annotations -- header matching, path rewriting, redirects, traffic splitting, timeouts, retries
-- are typed fields with schema validation, so a mistake is rejected at apply time rather than
ignored at runtime.

**Role separation is the structural change.** A `Gateway` is infrastructure: a platform team
declares the listeners, the addresses, the certificates, and *which namespaces may attach routes
to it*. An `HTTPRoute` is application configuration, living in the team's own namespace, naming
the Gateway it wants to attach to. The Gateway can refuse. That is a real permission model, where
Ingress had none -- any Ingress in any namespace could claim any hostname on a shared controller.

**It is not only HTTP.** `GRPCRoute`, `TLSRoute`, `TCPRoute` and `UDPRoute` cover the cases that
forced people into LoadBalancer Services, so a Postgres listener and a web application can share
one gateway object model. Weighted backends are first-class, which makes canary routing a
supported field rather than a controller-specific annotation.

**And it now covers east-west traffic too.** The GAMMA work lets an HTTPRoute attach to a Service
rather than a Gateway, so a service mesh can be configured with the same objects as the ingress
-- which removes one of the real costs of adopting a mesh, namely learning a second routing
vocabulary.

**Practical notes for adopting it.** The CRDs are installed separately and versioned separately
from Kubernetes, so the version of the standard and the version your implementation supports are
two facts to check. Implementations differ in conformance -- Envoy Gateway, Istio, Cilium,
Traefik, NGINX Gateway Fabric and the cloud controllers all support different subsets -- and the
conformance reports are the honest reference. Ingress continues to work, so migration is per
route, not per cluster.
