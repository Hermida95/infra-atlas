A ServiceAccount is a namespaced identity for processes. Every Pod runs as one -- the namespace's
`default` if none is named -- and the kubelet projects a token for it into the Pod at
`/var/run/secrets/kubernetes.io/serviceaccount/`. That token is a credential: present it to the
API server and you are that ServiceAccount, with whatever RBAC grants it has.

**The `default` ServiceAccount should have no permissions**, and in a modern cluster it has none
by default. The risk is the habit of binding something convenient to it "just for now": every
Pod in the namespace that did not specify an account then silently gains those permissions,
including Pods added a year later by someone else. Giving each workload its own ServiceAccount
with exactly its own grants costs one small object and removes that whole class of accident.

**Turn the token off when it is not used.** Most applications never call the Kubernetes API, and
mounting a credential into them is free attack surface -- a compromised container with a token can
at minimum enumerate whatever the account can see. `automountServiceAccountToken: false` on the
ServiceAccount (or on the Pod) removes it, and it is a sensible default to apply broadly and
exempt deliberately.

**Tokens are now short-lived, which fixed the worst property of the old model.** Projected tokens
are bound to an audience and expire, with the kubelet refreshing them in place. The legacy
`kubernetes.io/service-account-token` Secrets -- non-expiring, stored in etcd, valid until
deleted -- are no longer created automatically; making one with
`kubectl create token --duration` or by hand is a deliberate choice, and a long-lived one should
be treated like a password.

**Its second job is cloud identity.** IRSA on EKS, Workload Identity on GKE and the equivalents
elsewhere trust the cluster's OIDC issuer, so an annotated ServiceAccount's projected token can
be exchanged for a cloud role. That is how a Pod reads an S3 bucket with no access key anywhere
in the cluster -- and it makes the ServiceAccount the single place where a workload's identity,
inside and outside Kubernetes, is defined.
