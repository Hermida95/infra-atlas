RBAC answers one question: may this subject perform this verb on this resource. A Role or
ClusterRole lists permissions; a RoleBinding or ClusterRoleBinding attaches them to subjects --
users, groups or ServiceAccounts. Kubernetes stores no users, so a "user" is whatever
authentication produced, which is why you cannot list them and why group-based grants from an
OIDC provider are the normal shape for humans.

**It is purely additive, and that explains most confusion.** There are no deny rules. Effective
permission is the union of every binding that matches you, so narrowing access always means
finding and removing a grant, never adding a restriction. Someone with a ClusterRoleBinding to
`cluster-admin` cannot be restricted in one namespace by any object you can write.

**The one combination worth memorising** is a RoleBinding that references a ClusterRole: it grants
that ClusterRole's permissions *only within the binding's namespace*. That is how you reuse the
built-in `view`, `edit` and `admin` roles per team without writing them again, and it is the most
useful idiom in the system.

**`kubectl auth can-i` is the answer to every access question**, and it is underused.
`kubectl auth can-i create deployments -n team-a` for yourself,
`--as=system:serviceaccount:team-a:ci` for someone else, and `--list` for everything a subject
can do. It asks the API server to run the real evaluation, so it is not an approximation.

**The escalation paths are the part that matters for CKS**, and they are not obvious from the
verbs. `create pods` in a namespace lets you mount any Secret in it and run as any ServiceAccount
in it -- so it is effectively equivalent to reading those secrets. `escalate` and
`bind` let a subject grant permissions it does not itself have. `impersonate` is becoming someone
else. `get` on `pods/exec` is a shell in any Pod. And `patch nodes` or write access to a
mutating webhook configuration is cluster-wide control. Auditing a cluster means looking for
those, not for the word admin.
