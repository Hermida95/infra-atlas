Audit logging records every request the API server handles: the authenticated user, the verb, the
resource, the source IP, the authorisation decision, and -- depending on the level -- the request
and response bodies. Because every change in a cluster goes through the API server, this is the
complete record. Nothing else comes close: Events are controller commentary and expire in an
hour, and application logs know nothing about who called the API.

**It is off by default on a self-managed cluster** and requires a policy file and flags on the API
server, plus somewhere for the output to go (a file, rotated and shipped, or a webhook to a
collector). On managed clusters it is a switch -- EKS sends it to CloudWatch, GKE to Cloud
Logging -- and the common finding in an audit is that nobody turned it on.

**Writing the policy is the whole task**, because logging everything at RequestResponse is
unaffordable and logging nothing useful is the usual result of trying to be careful. A policy that
works: drop the noise first (`None` for watches, for the kubelet's own reads, for leases),
`RequestResponse` for a narrow high-value set (secrets, configmaps, RBAC objects, webhook
configurations), `Request` for workload writes, and `Metadata` as the catch-all. Rules are
evaluated in order and the first match wins, so the drops have to come first.

**It is also the tool for migrations and deprecations.** Filtering the log for a removed API
version tells you exactly which clients are still using it, with their user agents, which turns
an upgrade from a guess into a list. The same trick finds who is still using a ServiceAccount you
want to delete.

**Two things to get right.** The log must leave the control plane node -- an audit log that an
attacker with control plane access can edit is not evidence -- and it must be retained long
enough to be useful, which for a security log usually means a year rather than the two weeks a
default logging pipeline gives you.
