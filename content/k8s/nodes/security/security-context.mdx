`securityContext` exists at two levels: on the Pod, where it sets defaults and the fields that are
inherently Pod-wide (`fsGroup`, `runAsUser` defaults, `seccompProfile`, sysctls), and on each
container, where it can override and where the capability and privilege-escalation settings live.
Container-level values win.

**The baseline every workload should have** is short and worth applying by default:
`runAsNonRoot: true`, `allowPrivilegeEscalation: false`,
`capabilities: {drop: ["ALL"]}`, `seccompProfile: {type: RuntimeDefault}` and
`readOnlyRootFilesystem: true`. That is the `restricted` profile in practice, it breaks very
little, and it removes the overwhelming majority of container escape techniques, which depend on
a privileged context or a retained capability.

**`privileged: true` is the field that cancels everything else.** It gives the container all
capabilities, access to all devices, and disables the LSM and seccomp restrictions -- it is
root on the node with extra steps. The legitimate users are CSI node plugins, CNI agents and a
few monitoring agents. Anything else asking for it is asking for the cluster.

**`runAsNonRoot` versus `runAsUser` is a useful distinction.** `runAsUser: 1000` forces a UID,
which fails if the image's files are owned by someone else. `runAsNonRoot: true` only requires
that the image does not run as root, which pushes the decision into the image where it belongs --
the Dockerfile adds a `USER`, and the manifest asserts it. Using both is common; using only the
second is cleaner.

**The two fields that cause real friction** are the read-only root filesystem, which needs an
`emptyDir` mounted wherever the process writes (`/tmp`, a cache directory, sometimes
`/var/run`), and volume permissions: a non-root process cannot write to a freshly provisioned
volume unless `fsGroup` is set. On a large volume, the resulting recursive chown can delay Pod
start by minutes, which is what `fsGroupChangePolicy: OnRootMismatch` exists to avoid.
