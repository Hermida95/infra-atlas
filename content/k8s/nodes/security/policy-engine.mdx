A policy engine is an admission webhook with a policy language. Kyverno uses Kubernetes-style
YAML, which makes it approachable for anyone who writes manifests; Gatekeeper uses Rego through
OPA, which is more powerful and considerably steeper. Both validate, both mutate, and both
produce reports of what would fail.

**Mutation is the capability worth adopting one for.** Validation says no; mutation makes the
right thing happen by default. Adding a `securityContext` to every Pod that lacks one, pinning
every image to its digest, injecting required labels, setting a default
`ServiceAccount` with no token mount -- these turn policy from an obstacle into a platform
feature, and nothing built into Kubernetes can do them.

**Generation is the underrated one.** A rule that creates a default-deny NetworkPolicy, a
LimitRange and a ResourceQuota in every new namespace, and keeps them in sync, means a new team's
namespace is safe on the first day rather than after a review. That single policy is often the
whole justification for installing an engine.

**For plain validation, check whether you still need the webhook.**
ValidatingAdmissionPolicy evaluates CEL in the API server: no deployment, no certificates, no
availability risk, no latency. "Every Pod must set resource limits", "no `latest` tags", "images
only from our registry" are all one short expression. Keeping the webhook for the things only it
can do, and moving simple rules in-process, is the direction the ecosystem is going.

**And remember what a webhook costs.** It sits in the write path for everything it matches, so it
needs multiple replicas, a tight timeout, a narrow match rule, and
`kube-system` excluded -- or a bad day for the engine becomes a cluster that accepts no writes.
Running policies in `Audit` mode first is how you learn what would break without finding out the
hard way; both engines produce a report object listing every violation in the cluster, which is
also the fastest way to assess a cluster you have just inherited.
