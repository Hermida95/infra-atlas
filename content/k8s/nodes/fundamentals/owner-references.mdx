Each object can carry `metadata.ownerReferences`, a list of parents. The garbage collector in
the controller-manager watches for objects whose owners have all been deleted and removes them.
That is the whole mechanism behind "deleting a Deployment deletes its Pods" -- the Deployment
does not go around deleting things, it just stops existing, and a separate controller notices
the orphans.

**Cascade modes decide who waits for whom.** `--cascade=background` (the default) deletes the
parent immediately and lets the collector catch up, so the command returns before the Pods are
gone. `--cascade=foreground` puts a `foregroundDeletion` finalizer on the parent, so it stays
visible in `Terminating` until every dependent is gone -- which is what you want in a script
that must not proceed early. `--cascade=orphan` strips the references and leaves the children
running, which is occasionally the right tool for migrating Pods between controllers and
otherwise a way to create resources nobody owns.

**A reference is namespace-local and one-directional.** A namespaced object cannot be owned by
an object in another namespace, and a cluster-scoped object cannot be owned by a namespaced one;
Kubernetes will treat the reference as invalid and delete the child. This bites when an operator
in its own namespace creates something in a tenant namespace and sets itself as owner: the
object appears, then disappears, with an event nobody reads as the explanation.

**`blockOwnerDeletion`** on a reference makes foreground deletion of the parent wait for that
specific child. Operators use it to guarantee cleanup order -- drain before the StatefulSet
goes, deregister before the Service goes.

For debugging, `kubectl get <kind> <name> -o jsonpath='{.metadata.ownerReferences}'` answers
"what created this thing", which is the first question when you find a ReplicaSet nobody
remembers applying.
