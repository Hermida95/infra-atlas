kubectl is a client. Every command is one or more HTTP requests against the API server, and
`kubectl --v=8 get pods` prints them. Knowing this changes how you debug: a command that fails
is either a request that was rejected (RBAC, admission, validation) or a response you are
misreading, and the two look nothing alike once you can see the wire.

**Some behaviour is the client's, not the cluster's.** `kubectl apply` used to compute its diff
locally from the `last-applied-configuration` annotation -- so whether a removed field was
actually deleted depended on which tool wrote it last. `kubectl run` has changed meaning
repeatedly across versions. `kubectl rollout restart` is not an API verb; it patches an
annotation into the Pod template so the Deployment sees a change. None of this is wrong, but
none of it is portable to a controller or a CI script, which should talk to the API or use
server-side apply.

**The four commands that solve most problems** are `describe`, `logs --previous`, `get -o yaml`
and `get events --sort-by=.lastTimestamp`. In that order: describe tells you what the control
plane thinks, logs tell you what the process thinks, the raw object settles disagreements, and
the event stream shows what happened before the current state. A Pod stuck in `Pending` is
answered entirely by the first; a `CrashLoopBackOff` entirely by the second.

**Two flags worth a habit.** `--dry-run=server -o yaml` sends the object through validation,
defaulting, admission and mutating webhooks without persisting it, so you see what would
actually be stored -- including what a policy engine or a sidecar injector will do to it.
And `-o jsonpath` or `-o go-template` turns any query into a scriptable one line, which is how
you avoid parsing human output in a pipeline.

The one command to be careful with is `kubectl edit`. It works, and it leaves a cluster whose
state no longer matches git. For anything you intend to keep, edit the file.
