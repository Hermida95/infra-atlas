`metadata.finalizers` is a list of arbitrary strings. When you delete an object that has any,
the API server does not remove it: it sets `deletionTimestamp` and waits. Each controller that
put a name on the list is expected to do its cleanup and then take its own name off. When the
list is empty, the object is finally deleted. Until then it is visible, `Terminating`, and still
has to be reconciled.

**This is a correctness feature, not an obstacle.** `kubernetes.io/pvc-protection` is why
deleting a PersistentVolumeClaim that a Pod is still using does not rip the volume away.
A LoadBalancer Service's finalizer is why its cloud load balancer and security group are
deleted rather than left behind, billing. An operator's finalizer is how it deregisters an
external resource -- a DNS record, a cloud database, a cluster member -- before Kubernetes
forgets the object existed.

**The failure mode is a finalizer nobody will ever clear.** Uninstall an operator and its
custom resources keep its finalizer, so they can never be deleted, so the namespace holding
them can never finish terminating. The same thing happens with an admission webhook whose
service is gone: the controller cannot update the object to remove the finalizer, because
every write is rejected by a webhook that times out.

**The escape hatch and its cost.** `kubectl patch <kind> <name> -p '{"metadata":{"finalizers":null}}'
--type=merge` removes them and lets the deletion complete. It also skips exactly the cleanup the
finalizer was there to perform -- so the cloud load balancer stays up, the external database
survives, the node stays registered. Use it knowing what you are leaking, and prefer
reinstalling the controller long enough for it to clean up properly.

Diagnosing one is mechanical: `kubectl get <kind> <name> -o jsonpath='{.metadata.finalizers}'`
tells you which controller is being waited on, and the name almost always says who owns it.
