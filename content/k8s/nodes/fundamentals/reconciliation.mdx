`kubectl apply` does not deploy anything. It writes an object and returns. Some controller,
somewhere, later notices the write and starts trying to make reality match it -- and will keep
trying, with backoff, until it succeeds or you change the spec. Understanding this is the
difference between reading Kubernetes as a job scheduler and reading it as what it actually is:
a database with a lot of robots watching it.

**Level-triggered, not edge-triggered.** A controller does not process the event "replicas
changed from 3 to 5". It wakes up and asks "the spec says 5, how many are there?", which is why
a controller that was down for an hour does not need a backlog -- it reads the current state and
converges. It is also why there is no such thing as a failed command to retry: there is only a
spec that is not yet true.

**Every reconcile must be idempotent**, because it runs far more often than the number of real
changes: a re-list, a resync, another controller's status write, your own `kubectl label`. If a
reconcile creates something without first checking whether it exists, you get duplicates on the
second pass. This is the single most common bug in a first operator.

**Conditions are the readable form of the loop's state.** `Available`, `Progressing`,
`Ready` -- each with a status, a reason and a message. `observedGeneration` on status, compared
against `metadata.generation`, tells you whether the controller has even looked at your latest
edit yet; if they differ, the status you are reading answers an older question. When something
is stuck, those two numbers and `kubectl describe` are the first place to look, before logs.

The practical consequence is that there is no imperative path to fall back on. If a controller
is not running -- the operator is not installed, the controller-manager is down, RBAC denies it
the object -- then the object sits there, valid and accepted and completely inert, and nothing
in the output of `kubectl apply` hints at it.
