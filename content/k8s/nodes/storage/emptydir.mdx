`emptyDir` creates a directory on the node when the Pod is scheduled and deletes it when the Pod
is removed. It survives container restarts within the Pod, which makes it meaningfully different
from writing into the container filesystem, and it is shared by every container in the Pod that
mounts it.

**Its three good uses** are a cache or temporary workspace that can be rebuilt, a handover
directory between an init container and the app, and a writable path for an application that
insists on one while the root filesystem is read-only -- which is the pattern that lets you set
`readOnlyRootFilesystem: true` without rewriting the application.

**It is not storage, and the failure is silent until it is not.** Nothing warns you that the data
is ephemeral. A Pod running for three months accumulates state in an
`emptyDir`, and the first node upgrade reveals that it was never persistent. If the data matters
past the Pod's life, it needs a PersistentVolumeClaim.

**Size limits are the operational point.** By default an `emptyDir` can grow until the node's
disk is full, at which point the kubelet reports `DiskPressure` and starts evicting Pods --
including innocent ones on the same node. `sizeLimit` makes the kubelet evict the offending Pod
instead, which is a much better failure. The matching discipline is declaring
`ephemeral-storage` in requests and limits, so the scheduler accounts for it rather than
discovering it.

**`medium: Memory` changes the trade-off completely.** The directory becomes a tmpfs: fast, never
touching disk, and counted against the Pod's memory limit. That makes it the right place for
secrets you do not want written to node storage, and a trap for a workload that writes a
multi-gigabyte temporary file and is OOM-killed for it with no mention of the file anywhere in
the error.
