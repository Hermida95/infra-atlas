A StorageClass is the catalogue entry a claim picks from. It names a provisioner and carries the
parameters that provisioner needs, plus the three policy decisions that will apply to every
volume created through it: reclaim behaviour, binding mode, and whether expansion is allowed.

**A class is immutable after creation.** You cannot change its parameters -- you create another
class and migrate workloads to it, which for existing data means a snapshot and restore or a
copy. This is why the defaults you ship matter: `gp2` instead of `gp3` on AWS is a permanent
performance and cost difference for every volume anyone creates until someone notices.

**The default class is a cluster-wide decision with real consequences.** A claim with no
`storageClassName` gets whatever is annotated as default, and if there is none it stays
`Pending` with no obvious explanation. Having exactly one default, and having it be a sensible
general-purpose SSD with `WaitForFirstConsumer` and expansion enabled, removes a whole class of
support question. Two defaults is a configuration error that produces nondeterministic
behaviour.

**`reclaimPolicy: Delete` is the right default and the wrong one for databases.** With Delete,
deleting a namespace deletes the claims, which deletes the volumes, which deletes the data -- in
one command, with no confirmation. A separate `Retain` class used deliberately by stateful
workloads is cheap insurance, and it leaves the volumes behind as `Released` objects you have to
tidy up, which is the intended trade.

**Several classes is normal and worth doing.** A fast expensive class for databases, a general
one for everything else, a `ReadWriteMany` file class for the workloads that genuinely need
shared access, and a `Retain` variant for anything whose data must survive a mistake. Naming them
for what they are rather than for the disk type (`db-retain`, not `io2`) makes the manifests
self-documenting.
