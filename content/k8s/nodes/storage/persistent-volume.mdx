A PersistentVolume represents actual storage: an EBS volume, a Ceph RBD image, an NFS export, a
directory on a particular node. It is cluster-scoped, has a capacity, a set of access modes, a
reclaim policy, and a driver-specific source that identifies the real thing. It exists
independently of any Pod.

**You rarely create one now.** With a StorageClass and dynamic provisioning, a claim causes a
volume to be created to fit it, which is the normal path. Writing a PV by hand remains the
answer in two cases: adopting storage that already exists and must not be recreated (a restored
snapshot, a legacy NFS share), and local volumes pinned to specific nodes.

**Binding is exclusive and sticky.** One claim binds to one volume, and the pairing is recorded
on both. A volume that was bound and is now `Released` -- because its claim was deleted but its
reclaim policy was `Retain` -- will not be reused by a new claim even if it looks identical; the
stale `claimRef` has to be cleared first. That is the explanation for a PVC sitting in
`Pending` while an apparently suitable volume sits in `Released` next to it.

**Access modes are a property of the storage, not a wish.** `ReadWriteOnce` means one node at a
time, which is what every cloud block device offers, and it is the reason a Deployment with two
replicas and one block-backed PVC cannot have both Pods on different nodes.
`ReadWriteMany` needs a file protocol -- NFS, EFS, CephFS, Azure Files.
`ReadWriteOncePod` is the newer, stricter one: exactly one Pod, which is what a single-writer
database actually wants.

**For local storage, `nodeAffinity` on the volume is what makes it work.** A local PV declares
which node it lives on, and the scheduler will only place a Pod using it there. That is the
supported replacement for `hostPath`: the same performance, with the scheduler aware of the
constraint rather than discovering it as a failed mount.
