Kubernetes ships three minor versions a year and supports roughly the last three, which means a
cluster has to be upgraded two or three times a year, forever. There is no steady state. Teams
that treat it as a project rather than a routine end up several versions behind, at which point
the upgrade is genuinely hard because it has to be done repeatedly in sequence -- you cannot skip
minor versions.

**The version skew rules constrain the order.** The kubelet may be up to three minor versions
behind the API server but never ahead; the controller-manager and scheduler may not be ahead of
the API server either. So: control plane first, nodes after. On a multi-node control plane, one
node at a time, and the API server before the rest on each.

**The work that matters happens before the upgrade.** Removed APIs are what break things, and they
break *after* the upgrade, when a pipeline applies a manifest the server no longer understands --
long after the maintenance window closed. `pluto` or `kubent` against your manifest repositories
and your live objects produces the list, and the audit log filtered by removed API version tells
you which clients are still calling them. Fixing that list is the upgrade; the rest is mechanical.

**Nodes: upgrade in place or replace.** In place means cordon, drain, upgrade the kubelet and
runtime, uncordon -- and it leaves a node whose OS has accumulated state. Replacement means a new
node from a new image joins and the old one is drained and deleted, which is cleaner, tests your
ability to lose a node, and is what managed node groups and Karpenter do anyway. Replacement is
the better default if your workloads can take it, and the thing that proves they can is
PodDisruptionBudgets plus graceful shutdown.

**Add-ons are the step that is forgotten and then blamed on Kubernetes.** The CNI, the CSI
drivers, the ingress controller, CoreDNS, metrics-server and every operator have their own
supported ranges. Checking each one's compatibility matrix before the upgrade, and after, is
tedious and is where the surprises actually live -- a cluster that upgraded cleanly and lost its
storage driver is an upgrade that was not finished.

**Do it in a staging cluster first, and do it often.** The cost of each upgrade falls sharply
when they are small and frequent, and the cost of falling behind compounds.
