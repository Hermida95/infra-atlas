Kubernetes removes API versions on a schedule it publishes in advance: alpha versions can go in
any release, beta versions get a deprecation window, and GA versions are not removed within a
major version. The removals already behind us are instructive --
`extensions/v1beta1` Ingress and Deployment, `networking.k8s.io/v1beta1` Ingress,
`policy/v1beta1` PodDisruptionBudget, `batch/v1beta1` CronJob,
`rbac.authorization.k8s.io/v1beta1` -- and each one broke clusters whose owners thought the
upgrade had gone fine.

**The failure is delayed, which is what makes it dangerous.** Existing objects are converted and
keep working after the upgrade, because the API server stores one version and serves another. What
breaks is the next *write*: a CI pipeline applying a manifest with the removed
`apiVersion` gets a `no matches for kind` error, days later, to a team that changed nothing. The
cluster upgrade was last Tuesday and nobody connects the two.

**So the audit comes first, and there are three places to look.** Manifests in your repositories
(`pluto detect-files`, `kubent`), live objects in the cluster
(`pluto detect-api-resources`), and the audit log filtered by the deprecated version, which is
the only one that finds clients you have forgotten -- an old Terraform provider, a script on
someone's machine, a Helm chart pinned years ago.

**The API server warns you, if anything is listening.** Requests to deprecated versions get a
`Warning` header, which `kubectl` prints, and the
`apiserver_requested_deprecated_apis` metric exposes them with the release in which they will be
removed. An alert on that metric is the cheapest possible early warning, and almost nobody sets
it up.

**`kubectl-convert` does the mechanical part** of rewriting a manifest to a current version, which
is usually a one-line change. The work is finding them. And the discipline that prevents the
whole problem is not using beta APIs for anything long-lived, and upgrading often enough that a
removal is never more than one version away.
