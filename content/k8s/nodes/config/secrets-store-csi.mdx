The Secrets Store CSI driver is a CSI driver that serves secrets instead of disks. A
`SecretProviderClass` describes which values to fetch from which provider; a Pod mounts a volume
of this driver; the node plugin authenticates with the Pod's own identity, fetches the values, and
writes them as files into the mount. The Pod reads files. Nothing else in Kubernetes holds the
value.

**That "nothing in etcd" property is the reason to choose it.** The secret never becomes an API
object, so it is not in an etcd backup, not readable by anyone with `get secrets` in the
namespace, and not visible in an audit log as an object read. Combined with a projected token
exchanged for a cloud role, the chain from Pod to secret has no static credential and no stored
copy anywhere in the cluster.

**The cost is that it only works for file-based consumption.** Applications expecting
environment variables need the driver's optional secret-syncing feature -- which creates a real
Kubernetes Secret from the mounted value, and hands back exactly the property you adopted the
driver for. Adopting it properly often means a small application change, and that is the honest
trade against External Secrets Operator, which needs none.

**Rotation support is per provider and worth checking.** The driver can poll and update the
mounted files, so a rotated secret reaches the Pod without a restart -- but the application still
has to re-read the file, which most do not. For credentials that rotate often, the realistic
design is either an application that watches its secret files, or a sidecar that refreshes a
token the application reads on each use.

**It is also a privileged node component**, like any CSI node plugin, and a Pod's mount failing
means the Pod does not start -- so the driver is in the critical path of every workload that uses
it. More than one replica of its provider components, and an alert on mount failures, are the
minimum operational care.
