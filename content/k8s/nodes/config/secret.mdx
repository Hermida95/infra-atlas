A Secret is structurally identical to a ConfigMap: keys to values, consumed as environment
variables or as files. The differences are base64 encoding in the API representation, a separate
RBAC resource name, the kubelet keeping them in tmpfs rather than on disk, and -- if someone
configured it -- encryption at rest in etcd.

**Base64 is not encryption**, and this has practical consequences people discover late. Without
an `EncryptionConfiguration` on the API server, a Secret is stored in etcd as readable text:
anyone who can read an etcd snapshot, or an etcd backup sitting in an S3 bucket, has every
credential in the cluster. Enabling encryption at rest with a KMS provider is the first item on
any serious hardening list.

**RBAC on Secrets is all-or-nothing per namespace.** There is no way to grant read access to one
Secret and not another with core RBAC -- `get` on `secrets` in a namespace is `get` on all of
them. So the unit of secret isolation is the namespace, which is an argument for separating
workloads that hold materially different credentials.

**Files beat environment variables, for three reasons.** An environment variable is visible in
`/proc/<pid>/environ` to anything in the Pod, is commonly dumped into logs and crash reports by
frameworks, is inherited by child processes, and cannot be rotated without replacing the Pod. A
mounted Secret is updated in place when the object changes, is readable only by the processes
that open the file, and does not leak into a stack trace.

**The real answer for most teams is not to store the value in Kubernetes at all.** External
Secrets Operator or the Secrets Store CSI driver keep the source of truth in AWS Secrets Manager,
Vault or an equivalent, with audit, rotation and fine-grained access control the Secret API does
not have. And for cloud API access specifically, workload identity -- IRSA, Workload Identity --
removes the credential entirely, which is better than protecting it.
