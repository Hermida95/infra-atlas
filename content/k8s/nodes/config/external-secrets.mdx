The Secret API has three gaps that matter in production: no rotation, no per-secret access
control inside a namespace, and no audit of who read what. Every serious setup therefore keeps the
authoritative value in a dedicated manager -- AWS Secrets Manager, Vault, Azure Key Vault, GCP
Secret Manager -- and brings it into the cluster on demand.

**External Secrets Operator is the syncing approach.** You write an `ExternalSecret` naming a
`SecretStore` and the keys you want; the operator fetches them and creates a normal Kubernetes
Secret, refreshing it on an interval. Workloads consume it as they always did, nothing in the
application changes, and the git repository contains only a reference -- which is what makes
GitOps workable for secrets. The cost is that the value does end up in etcd, so encryption at
rest still matters, and rotation is eventually-consistent: the Secret is updated on the next
refresh, and whether the Pod notices depends on whether it mounted the Secret as a file or an
environment variable.

**The CSI approach never creates a Secret at all**, mounting the value straight from the store
into the Pod's filesystem. Nothing is in etcd, which is a stronger position, and the application
must read from a file.

**Authentication is the part worth getting right.** The pattern that avoids a bootstrap secret is
a projected ServiceAccount token with the store's audience, exchanged for a cloud role --
IRSA on EKS, Workload Identity on GKE, Vault's Kubernetes auth method. Then the cluster holds no
credential for the secret store either, and access is attributable to a specific ServiceAccount
in a specific namespace, which is what makes the audit log useful.

**Two practical warnings.** The operator becomes a dependency of every workload start that needs
a secret, so it wants more than one replica and monitoring on its sync failures -- a silently
failing refresh means a credential that is quietly out of date. And the per-secret access control
you gained lives in the external store's policies, so it only exists if someone writes those
policies narrowly rather than granting the cluster one wildcard read.
