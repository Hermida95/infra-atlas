A kubeconfig answers three questions: which API server, as whom, and in which namespace by
default. The file at `~/.kube/config` is one of possibly several --
`KUBECONFIG` takes a colon-separated list and merges them -- and `kubectl config view --flatten`
prints the merged result, which is the only reliable way to see what you actually have.

**Identity is in the file, not in the cluster.** Kubernetes stores no users, so a kubeconfig is
the credential. A client certificate in it is a bearer of whatever groups are in its subject,
until it expires, with no way to revoke it short of rotating the CA. That is why certificates
are for break-glass and bootstrap, and why every managed provider uses an `exec` credential
plugin instead -- `aws eks get-token`, `gke-gcloud-auth-plugin` -- which mints a short-lived
token on each call from a cloud identity you can actually revoke.

**The operational hazard is `current-context`.** It is global mutable state shared by every
terminal on the machine, so `kubectl delete` run in the window you forgot about goes to the
cluster you switched to an hour ago. The habits that fix it: a prompt that shows context and
namespace (`kube-ps1`, `starship`), one kubeconfig file per cluster selected with
`KUBECONFIG` in that shell rather than switching a shared file, and `--context` spelled out in
anything scripted. Production access worth separating is worth a separate file.

**For CI, a kubeconfig is a secret with a scope.** It should carry a ServiceAccount token bound
to a role that can do exactly what the pipeline does, in exactly the namespaces it owns -- not a
cluster-admin certificate, which is what gets pasted into a CI variable when nobody is watching.
`kubectl auth can-i --list` run with that config is the quickest audit of what you just handed
out.
