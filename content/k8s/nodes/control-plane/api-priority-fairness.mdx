Before APF, the API server had two numbers: maximum in-flight mutating requests and maximum
in-flight read requests. Exceed either and requests were rejected indiscriminately -- so an
operator listing every Pod every second could push the kubelets' heartbeats out of the server
and take the cluster `NotReady`. The fix was not more capacity but fairness.

**Every request is classified, then queued.** A FlowSchema matches on identity and resource and
routes the request to a PriorityLevelConfiguration; within a level, requests are distributed
across queues by a flow key so that one noisy client occupies one queue rather than all of them.
Levels have concurrency shares, so `leader-election` and `system` traffic is protected from
`global-default`, and the `exempt` level bypasses queuing entirely.

**What you see when it engages is a 429** with `Retry-After`, and kubectl saying it is being
throttled. That is the system working: the request was deliberately shed to protect something
more important. The wrong reaction is to raise the limits; the right one is to find the client.
The `apiserver_flowcontrol_*` metrics -- rejected requests and queue length by priority level
and FlowSchema -- name it directly, and almost always it is one controller doing unbounded
`list` calls where it should be using an informer's cache.

**Tuning is rarely the answer, but it is available.** You can give a critical in-house controller
its own FlowSchema and priority level so it is not competing in the default pool, or cap a
known-abusive integration into a small level of its own. Both are better than the alternative
people reach for first, which is adding API server replicas to absorb traffic that should not
exist.

For anyone writing controllers, the lesson is upstream of all of this: watch, do not poll; use a
shared informer; set a resync period in minutes, not seconds; and page through large lists.
APF is a seatbelt, not a licence.
