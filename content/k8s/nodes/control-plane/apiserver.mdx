The API server is the cluster. Every other component -- the scheduler, the controllers, every
kubelet, your kubectl, every operator -- is a client of it, and none of them talk to each other
directly or to etcd. That single-front-door design is what makes the system auditable and
extensible, and it is also why API server availability is cluster availability for anything
that needs to change.

**Requests walk a fixed chain:** authenticate, authorise, mutate, validate, validate again,
store. Knowing the order turns error codes into diagnoses. A 401 means your identity did not
resolve -- expired certificate, wrong token. A 403 means RBAC has no rule for that verb on that
resource, and the message names them both. A 422 is schema validation. A rejection that mentions
a webhook is admission, and that is the one that can fail for reasons entirely outside your
manifest.

**Running Pods do not need it.** If the API server is down, containers keep running, kubelets
keep restarting what crashes locally, and kube-proxy keeps forwarding with the rules it already
has. What stops is change: no scheduling, no scaling, no rollout, no new endpoints, no
`kubectl`. This is a genuinely good property, and it is why "the control plane is down" is an
incident but not necessarily an outage.

**It is horizontally scalable and stateless.** Three replicas behind a load balancer is the
normal HA shape, each talking to the same etcd quorum. The watch cache in each replica is what
makes thousands of watching clients affordable; a client that polls `list` instead of watching
is the classic way to melt a control plane, which is what API Priority and Fairness now
contains.

For security, three things on this component matter more than anything inside the cluster:
encryption at rest for Secrets, an audit policy that actually records writes, and no anonymous
or insecure port. Everything in CKS that is not about Pods is about this list.
