The controller-manager is a single process hosting dozens of independent controllers, each a
loop over one resource kind. There is nothing special about them: they use the same API, the
same watches and the same status-writing discipline an operator you write would use. Reading
their behaviour as "Kubernetes does X" hides the fact that some specific loop does X, with its
own timings and its own failure modes.

**Leader election, not sharding.** All the loops run in one elected leader, which holds a Lease
object and renews it. The other replicas sit idle waiting for the lease to expire. So HA here
means failover in a few seconds, not more throughput, and a controller-manager that is CPU-bound
needs a bigger node rather than another replica.

**Its timings explain things that look like bugs.** A node that loses its kubelet is not marked
`NotReady` instantly -- it is marked after the heartbeat grace period, and its Pods are not
deleted until the `node.kubernetes.io/unreachable` toleration expires, which defaults to five
minutes. That five minutes is why a hard node failure takes so much longer to heal than a Pod
crash, and why workloads that need faster failover shorten
`tolerationSeconds` themselves rather than waiting for the default.

**It needs very wide permissions**, because it acts on behalf of every controller inside it,
and it is the reason cloud credentials used to sit in the control plane: the cloud-specific
loops were originally in here. Those have moved out into the cloud-controller-manager, which is
why a modern cluster can run the generic control plane with no provider credentials at all.

For debugging, `kubectl -n kube-system logs <controller-manager-pod>` plus the controller name
in the log line tells you which loop is unhappy, and its `/metrics` endpoint exposes per-loop
work queue depth and retry rates -- the honest measure of whether the control plane is keeping
up with the cluster.
