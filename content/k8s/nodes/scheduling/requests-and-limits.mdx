Requests and limits are not two ends of a range; they answer different questions. A request is
what the scheduler reserves for you -- it decides whether your Pod fits on a node, and nothing
else can use what you reserved. A limit is what the kernel will not let you exceed at runtime.
A Pod can request 100m of CPU, be scheduled on that basis, and happily use two whole cores if the
node is idle and its limit allows.

**CPU and memory enforce differently, and the asymmetry drives the standard advice.** Exceeding a
memory limit kills the container immediately. Exceeding a CPU limit throttles it: the kernel
stops scheduling your threads until the next period, which shows up as p99 latency with no error
anywhere. The most common real-world damage comes from the second -- a JVM or a Go runtime that
sizes its thread pool from the number of visible cores, given a 500m limit, spends most of its
time throttled. Hence the widely used pattern: **always set memory requests and limits equal,
always set a CPU request, and think twice before setting a CPU limit at all.**

**Requests are what cost money.** The scheduler packs nodes by request, so a cluster where every
workload requests twice what it uses needs twice the nodes, permanently, while every dashboard
shows 30% utilisation. Measuring actual usage over a week and setting requests near the p95 is
the single highest-return piece of cluster work there is -- and the Vertical Pod Autoscaler in
recommendation mode exists to produce exactly those numbers.

**The units bite once per career.** CPU is cores: `1` is one core, `1000m` is the same thing,
`100m` is a tenth. Memory is bytes with binary suffixes: `Mi` is 1024-based, `M` is 1000-based,
and `500m` of memory means half a byte -- a typo the API accepts and nothing warns about. CPU is
compressible and memory is not, which is the underlying reason they are enforced so differently.

**A Pod with neither** is BestEffort: it schedules anywhere, is throttled by nothing, and is the
first thing killed when the node fills. That is a reasonable choice for a nightly batch job and
a bad one for anything serving traffic, which is why a LimitRange with sensible defaults is worth
having in every namespace.
