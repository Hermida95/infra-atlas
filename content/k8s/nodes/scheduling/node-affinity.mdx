Node affinity is `nodeSelector` with a grammar. It lets you say "in zone a or zone b", "any
instance type not in this list", "a node with a GPU count greater than 2", and -- crucially --
"prefer this, but run anyway if you cannot".

**Required versus preferred is the distinction to internalise**, because it decides your failure
mode. A required rule is a filter: the scheduler discards every node that does not match, and if
none are left the Pod waits as `Pending` indefinitely. A preferred rule is a score: the scheduler
ranks nodes, adds the weight where the rule matches, and places the Pod on the best survivor --
so an unsatisfiable preference is silent, and you discover it by noticing all your replicas are
in one zone.

**`IgnoredDuringExecution` is in both names and means what it says.** Affinity is evaluated when
the Pod is scheduled and never again. Remove the label from the node and the Pod keeps running
there happily. There has never been a `RequiredDuringExecution` variant, so if a Pod must leave a
node when conditions change, the mechanism is a taint with `NoExecute`, not affinity.

**The syntax has one real trap.** Under `required`, the list of `nodeSelectorTerms` is ORed while
the `matchExpressions` inside one term are ANDed. So two terms means "either of these shapes" and
two expressions in one term means "both of these labels" -- and writing the one you did not mean
produces a rule that is either far too permissive or impossible to satisfy, with no error either
way. `kubectl describe pod` on a Pending Pod is the only feedback.

**With a node provisioner it becomes a buying decision.** Karpenter and the cluster autoscaler
read a pending Pod's affinity to decide what to launch: a required `arch: arm64` means a Graviton
instance appears, a required zone means it appears there. That makes affinity the interface
between a workload's needs and your cloud bill, and a stray required constraint an expensive one.
