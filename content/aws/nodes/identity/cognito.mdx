Cognito exists because IAM is not for your users. IAM principals are a small, administrative
population; an application with fifty thousand customers needs a directory, not fifty thousand
IAM users -- and the account quota would stop you anyway at five thousand.

A **user pool** is that directory. It holds the accounts, enforces the password policy and MFA,
runs the sign-up and sign-in flows (including a hosted UI you can skin), and federates to
Google, Apple, SAML or any OIDC provider so a user can bring an identity they already have. The
output is a set of JSON Web Tokens. Your backend never sees a password: it validates the token's
signature against the pool's public keys and reads the claims.

An **identity pool** does something else entirely, and the similar name is the whole problem. It
takes a token -- from your user pool, or straight from Google, or none at all for a guest -- and
exchanges it for temporary AWS credentials through STS. That is how a mobile app uploads
straight to a per-user S3 prefix with no backend in the path. If the question is *"let my users
sign in"*, it is a user pool. If it is *"let my users call AWS directly"*, you need both.

Two things worth remembering for an exam. First, API Gateway has a built-in **Cognito
authorizer**: point it at the user pool and unauthenticated requests are rejected at the edge of
the API, before any of your code runs. Second, **pre-token-generation** and the other Lambda
triggers are where custom claims get added -- a tenant id, a plan tier -- so your authorisation
logic reads the token instead of querying a database on every request.
