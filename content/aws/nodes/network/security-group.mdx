A security group is a firewall attached to an elastic network interface, not to an instance and
not to a subnet. One interface can carry several groups and the rules are additive: the union of
every group's allows, with no ordering and no deny. That last part is the one people fight:
there is no way to say "everyone except this address" in a security group, because there is no
deny rule. If the requirement is to block something specific, the answer is a network ACL at
layer 3 and 4, or WAF above it.

**Stateful** means the return path is implicit. Allow inbound 443 and the response goes back out
whatever the outbound rules say; allow outbound 443 and the response comes back in. This is the
difference from a network ACL, where every flow needs a rule in both directions plus one for the
ephemeral port range, and forgetting the second half is the classic broken-NACL afternoon.

The feature worth building designs around is **referencing another group as the source**. A
database group whose inbound rule is "port 5432 from `sg-app`" keeps working as the application
scales from two instances to two hundred, moves zones, or is replaced entirely -- there is no
address list to maintain and no CIDR that is wider than it should be. Chain them: internet to
the ALB's group, the ALB's group to the app's group, the app's group to the database's group.
Each tier can only be reached from the one in front of it, and nothing in the design mentions an
IP address.

Defaults to know. A new group denies all inbound and allows all outbound. The **default**
security group of a VPC additionally allows all traffic from itself, which quietly means every
resource that lands on it can talk to every other -- do not use it. Limits are per interface
(five groups by default) and per group (sixty rules each way), and a rule referencing a group
counts as one rule however many instances are in it.
