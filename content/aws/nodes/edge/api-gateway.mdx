API Gateway is a managed front door: it terminates TLS, authorises, throttles, validates,
transforms and routes, so none of that lives in your code. It also has two distinct products and
one WebSocket one, and the first decision is which.

**HTTP API** is the newer one: roughly 70% cheaper, lower latency, and enough for most
serverless APIs -- JWT authorizers, CORS, Lambda and HTTP integrations, private integrations
through a VPC link. **REST API** is the original and keeps the features HTTP API does not have:
**response caching**, **usage plans and API keys** for per-customer quotas, request and response
**transformation** with mapping templates, **request validation** against a schema, **WAF**
integration, **private** endpoints reachable only through a VPC endpoint, and **canary
deployments**. The honest rule: start with HTTP API, and move to REST when you need something on
that list.

**Authorizers** are where the security boundary belongs. A **Cognito** authorizer validates the
user pool's JWT; a **Lambda authorizer** runs your own logic and returns an IAM policy, with
caching so it does not run on every request; **IAM** auth signs requests with SigV4, which is
right for service-to-service. In all three cases an unauthorised request is rejected at the
gateway and never reaches the function -- which is both a security property and a cost one.

**Direct service integrations** remove functions that exist only to forward. A REST API can
`PutItem` into DynamoDB, publish to SNS, send to SQS or start a Step Functions execution with no
Lambda in the path: less latency, less cost, nothing to patch.

The limits to design around: a hard **29-second integration timeout** (so a long job must be
asynchronous -- accept, enqueue, return a job id), 10 MB payloads, and per-account throttling
defaults of 10,000 requests per second with a 5,000 burst. Endpoint types matter too: *regional*
is the default, *edge-optimised* routes through CloudFront, and *private* is reachable only from
inside a VPC through an interface endpoint.
