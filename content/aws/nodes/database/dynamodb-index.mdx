In a relational database you model the entities and write queries later. In DynamoDB you list
the access patterns first and design the keys to serve them, because there is no query planner
to rescue a bad choice: an access pattern the keys do not support becomes a **Scan**, which
reads the entire table.

The **partition key** is hashed to pick a physical partition. Everything about performance
follows from how evenly it spreads. A key like `country` on a table where 80% of rows are one
country gives you a hot partition that throttles while the rest of the table is idle. Keys with
high cardinality -- a user id, an order id -- spread well. When a naturally skewed key is
unavoidable, **write sharding** adds a suffix (`2024-01-15#3`) to spread one logical key over
several partitions, and reads fan out across the shards.

The **sort key** is what makes DynamoDB more than a key-value store. Within a partition, items
are ordered by it, so you can query a range: all orders for this customer between two dates, all
events whose key `begins_with` a prefix. The composite-key pattern -- storing several entity
types in one table with keys like `USER#123` / `ORDER#2024-01-15` -- is **single-table design**,
and it exists so that one query returns a customer and their recent orders together rather than
two round trips.

Indexes cover the patterns the main key cannot. A **local secondary index** keeps the same
partition key with a different sort key; it is strongly consistent, shares the table's capacity,
must be created with the table, and caps each partition at 10 GB. A **global secondary index**
has an entirely different partition key, can be added at any time, has its own capacity, and is
eventually consistent -- it is effectively a second table that DynamoDB keeps in step. GSIs are
the usual answer; LSIs are rare.

Two traps with GSIs. **Projection** decides what the index stores: keys-only is cheap but means
a second read to fetch the rest of the item, while projecting everything doubles the storage.
And if a GSI is **throttled** on writes, the write to the base table is throttled too -- an
under-provisioned index can take down the table it belongs to.
