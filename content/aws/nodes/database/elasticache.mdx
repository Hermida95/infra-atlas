The cheapest way to take read load off a database is to stop asking it the same question twice.
ElastiCache is the managed place to put the answer, and the engine choice is mostly settled:
**Redis** (or its fork Valkey) unless you specifically want Memcached's multi-threaded
simplicity, because Redis brings replication, automatic failover, persistence, sorted sets,
pub/sub and transactions.

The patterns are worth naming because exam questions describe them rather than name them. **Lazy
loading** (cache-aside): read the cache, miss, read the database, write the cache. Only
requested data is cached, and every miss pays a round trip; stale data lives until it is
evicted. **Write-through**: write the cache whenever you write the database. Reads are never
stale, writes cost more, and data that is never read is cached anyway. Most systems do both,
with a **TTL** on everything as the safety net -- a TTL is what stops a missed invalidation
being permanent.

Beyond caching, Redis is used for things that are awkward elsewhere: **session stores** for a
stateless web tier, **rate limiting** with counters and expiries, **leaderboards** with sorted
sets, and a simple **pub/sub** bus.

For availability, cluster mode disabled gives you one shard with replicas and a **Multi-AZ**
option with automatic failover; cluster mode enabled splits the keyspace across shards so you
can exceed one node's memory and spread the write load. Serverless removes the sizing question
entirely and is the sensible starting point for a new workload.

The thing to remember from an exam's point of view: ElastiCache is **in front of** a database,
not instead of it, it does nothing for availability of the data itself, and against DynamoDB
specifically **DAX** is usually the better cache because it invalidates itself.
