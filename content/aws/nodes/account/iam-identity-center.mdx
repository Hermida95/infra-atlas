Identity Center is how humans should reach AWS. A person authenticates once against the identity
source -- your Active Directory, Okta, Entra, Google Workspace, or Identity Center's own
directory -- and the portal then lists the accounts and roles they are entitled to. Picking one
assumes a role through STS and hands back credentials that expire.

The mechanics worth knowing: a **permission set** is a definition that Identity Center
materialises as an **IAM role** in each account it is assigned to. So the thing a person assumes
is an ordinary role, with an ordinary trust policy, visible in that account -- there is no
magic, and CloudTrail records it normally. Assignments are made to **groups** and to **OUs**
rather than to users and accounts, which is the difference between an access model that survives
growth and one that is edited every time someone joins.

Two features that remove persistent credentials from developer machines. `aws sso login` gives
the CLI a session from the same sign-in, so no access key is stored in `~/.aws/credentials`. And
**attribute-based access control** passes directory attributes -- department, cost centre,
project -- as session tags, so one permission set can grant access scoped by tag instead of
needing a permission set per team.

It also supports **SCIM provisioning**, so joiners, movers and leavers in the HR-backed
directory flow through automatically. That is the control an auditor asks about: when someone
leaves, their AWS access ends because their directory account ended, not because somebody
remembered.

The position to hold: IAM **users** are for the small number of cases that genuinely cannot
federate -- a legacy integration, an emergency break-glass account with MFA and heavy
monitoring. Everything else, human or machine, is a role.
