A service control policy is a ceiling. It never grants a permission -- it only limits what the
IAM policies inside a member account are able to grant. A user with `AdministratorAccess` in an
account whose SCP allows only S3 and CloudWatch can use S3 and CloudWatch, and nothing else.

Policies attach to the organization root, an OU or an individual account, and they are inherited
down the tree. A request must be permitted by every SCP on the path from the root to the
account, plus the account's own IAM. The **management account is exempt** from SCPs entirely,
which is the single best argument for running no workloads in it.

Two styles. **Deny lists** start from the default `FullAWSAccess` and subtract specific actions
-- this is what nearly everyone uses, because it keeps working when AWS launches a service.
**Allow lists** replace the default with an explicit set, which is precise and requires a change
every time a team adopts something new.

The guardrails worth having, almost regardless of organisation: deny every region except the
ones you operate in, with `aws:RequestedRegion`; deny disabling CloudTrail, GuardDuty, Config
and Security Hub; deny deleting or modifying the log archive bucket; deny leaving the
organization; deny creating IAM users and access keys, so people federate; deny making a
snapshot or AMI public. Each of those closes a class of incident that cannot then happen by
mistake.

Two details that cause confusion. SCPs do not apply to **service-linked roles**, so a policy
that looks ignored may be hitting one. And because they are a ceiling, an SCP alone changes
nothing visible until someone tries the thing it denies -- test them in a sandbox OU first,
because the symptom of an over-broad SCP is a wide, unexplained `AccessDenied` across an
account.
