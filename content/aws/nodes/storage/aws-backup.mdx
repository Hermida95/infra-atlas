Every AWS storage and database service has its own backup mechanism, each with its own
scheduling, retention and permissions. AWS Backup is the layer that makes them one policy: EBS,
EC2, RDS, Aurora, DynamoDB, EFS, FSx, S3, Storage Gateway, DocumentDB, Neptune and Redshift
under a single plan, a single vault and a single audit trail.

The feature that changes how an organization works is **assignment by tag, applied across the
organization**. A backup policy attached to an OU, selecting resources tagged `Backup=daily`,
means a database created next month by a team you have not met is backed up without anyone
remembering to configure it. Backup Audit Manager then reports on what is not covered, which is
the question nobody can otherwise answer.

**Cross-region and cross-account copies** are what make it a disaster-recovery tool rather than
an undo button. The standard shape is a backup account that no workload administrator can reach,
holding copies, with **Vault Lock in compliance mode** so the retention period cannot be
shortened by anyone -- including the root user, including AWS Support. That combination is the
honest answer to a ransomware requirement, because it is the only configuration where an
attacker with full administrative access in the source account still cannot destroy the copies.

The part most plans skip is **restore testing**. AWS Backup can run scheduled restores
automatically and validate them, which is the difference between believing you have backups and
knowing. Pair it with the recovery objectives: a backup plan is only correct if its frequency
meets the RPO and its restore time meets the RTO, and the second of those can only be
established by doing it.
