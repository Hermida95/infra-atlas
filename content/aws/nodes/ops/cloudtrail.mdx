CloudTrail records API calls: the identity that made it, the time, the source IP, the parameters
and the response. It is the answer to "who deleted that", and it is also the data GuardDuty,
Detective and half of Security Hub read.

**Event history** in the console gives the last 90 days of management events for free, in the
current account and region, with no configuration. It is enough for a quick question and not
enough for an audit, because it does not persist, cannot be aggregated and omits data events.

A real setup is an **organization trail**: created once in the management account, applied to
every member account including future ones, and not disableable from inside them. It writes to
an S3 bucket in a **separate log archive account** that no workload administrator can reach,
with **Object Lock** for immutability and an SCP forbidding anyone from modifying the trail or
the bucket. That combination is what makes the record trustworthy, and it is the shape Control
Tower sets up for you.

**Data events** are the decision with a cost attached. Management events are cheap; S3
object-level and Lambda invocation events are charged per event and can be voluminous. They are
also, almost always, what an investigation actually needs -- "which objects did this role read"
is a data event question. The usual compromise is to enable them selectively: sensitive buckets,
specific prefixes, specific functions, using advanced event selectors.

Two features worth naming. **CloudTrail Lake** stores events in a managed lake queryable with
SQL for up to ten years, which removes the Athena-plus-Glue pipeline for most people.
**Insights** detects unusual rates of API calls -- a sudden spike in `RunInstances` or
`DeleteObject` -- and raises them as events.

Finally, the distinction exams test: CloudTrail says *who did it*, Config says *what it looked
like before and after*, and CloudWatch Logs holds *what the application printed*. Three
different questions, three different services.
