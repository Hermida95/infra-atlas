Config records the configuration of your resources and keeps the history. For any resource it
can answer: what does it look like now, what did it look like last Tuesday, what changed between
the two, and what else is related to it. CloudTrail says who made the call; Config shows the
before and after.

On top of that history sit **rules**. A rule evaluates resources and marks them compliant or
not: `s3-bucket-public-read-prohibited`, `encrypted-volumes`,
`rds-instance-public-access-check`, `required-tags`. There are hundreds of managed ones, and
custom rules can be a Lambda function or a **Guard** policy-as-code file. Rules trigger on
configuration change, on a schedule, or both.

The part that makes it more than a report is **remediation**: a rule can be wired to an SSM
Automation document that fixes the resource. `required-tags` with automatic remediation is how a
tagging policy stops being a wiki page nobody follows; a public-bucket rule with automatic
remediation closes the bucket in seconds rather than at the next review.

Across an organization, deploy rules as **conformance packs** through the organization API and
aggregate the results into an **aggregator** in the audit account. That is the only way to
answer "is the estate compliant" as one number. Security Hub's compliance scores are built on
exactly this, which is why Config has to be recording for those scores to mean anything.

The cost is the thing to plan. Config charges per **configuration item recorded** plus per rule
evaluation, and a busy account with everything recorded is not cheap. Scope the recorder
deliberately -- exclude high-churn resource types you do not audit, consider daily recording for
some -- rather than switching it off, because the alternative is having no history on the day
you need it.
