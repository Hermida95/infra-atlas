GuardDuty is the easiest security win on AWS: turn it on and it starts analysing logs it reads
itself. There is no agent, no log configuration, no cost for the logs it consumes, and no effect
on your own CloudTrail or flow log settings.

What it actually does is correlate those sources against threat intelligence and behavioural
models. The findings are the interesting part because they describe things no rule would have
caught: an instance's credentials being used from an IP address outside AWS
(`UnauthorizedAccess:EC2/InstanceCredentialExfiltration` -- almost always an SSRF against
IMDSv1), DNS queries to a cryptomining pool, an API call from an anonymising proxy, a previously
unseen principal enumerating IAM, or a sudden burst of S3 reads by a role that never reads S3.

Getting it right organisationally is one decision: enable it from a **delegated administrator**
account for the whole organization with auto-enable for new accounts. Enabled per account by
hand, it will cover some and miss the one that matters.

Findings are **EventBridge events**, which is where the value compounds. A high-severity finding
can create a ticket, page someone, snapshot and isolate an instance by swapping its security
group, or revoke the role's sessions -- automatically, in seconds. Severity-based routing avoids
alert fatigue: the low-severity stream is large and mostly informational.

Around it: findings aggregate into **Security Hub**, **Detective** builds the graph for the
investigation that follows, and the optional protection plans (S3, EKS runtime, malware
scanning, RDS, Lambda) each add cost and coverage. Suppression rules exist for the findings your
architecture produces on purpose, such as a legitimate scanner.
