Secrets Manager stores a secret encrypted with KMS and hands it out through IAM. So does
Parameter Store, free. What you are paying roughly $0.40 per secret per month for is
**rotation**, and if nothing rotates you are paying for nothing.

Rotation is a Lambda function following a four-step contract: `createSecret` generates the new
value, `setSecret` applies it to the database, `testSecret` verifies it works, and
`finishSecret` moves the `AWSCURRENT` label. AWS supplies ready-made functions for RDS, Aurora,
Redshift and DocumentDB; for anything else you write it. The **alternating users** strategy --
two database users, rotating one while the other serves -- is what makes rotation zero-downtime,
because there is never a window where the current credential is invalid.

The retrieval detail that matters in production: `GetSecretValue` is a network call and it is
billed per ten thousand. Calling it on every request is slow and expensive. Use the **Lambda
extension** or the **ECS/EKS secrets integration**, which cache locally, or cache in your own
code with a refresh. The ECS task definition can inject a secret straight into an environment
variable, which is the cleanest option and keeps it out of the image and out of the task
definition's plaintext.

Two other features earn their place. **Cross-region replication** means a disaster-recovery
region reads the secret locally rather than depending on the failed region. And **RDS Proxy**
integration means the function never sees the credential at all -- it authenticates to the proxy
with IAM, and the proxy reads the secret.

The decision against Parameter Store: rotation, cross-region replication, and generating random
passwords. Without those, Parameter Store's SecureString is the same KMS encryption for free.
